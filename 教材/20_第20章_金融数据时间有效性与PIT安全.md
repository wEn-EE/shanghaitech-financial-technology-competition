# 第20章 金融数据时间有效性与PIT安全

> 本章实验使用SYNTHETIC人工宏观数据与人工处理时刻。真实统计发布制度仅用于解释为什么必须保存版本；示例数值、发布时间、处理延迟和状态阈值均不是官方数据。PIT安全在本章指信息时间上的可用性约束，不等同于网络安全或投资安全。

## 20.1 事件时间、发布时间、获取时间与计算完成时间

### 20.1.1 同一条数据的多个时间

**截至时点安全（Point-in-Time Safety，PIT安全）**要求：在历史决策时点重建输入时，只使用当时按照明确可用性规则能够取得的信息及版本。

它不是简单的“按日期排序”，也不是“训练集放在测试集之前”。一张按月份排序的最新GDP表，仍可能把数年后修订的历史值放到几年前的训练样本中。

建议将时间拆为以下字段。字段名是本书的工程约定，接入具体供应商时必须建立映射。

| 字段 | 含义 | 一个典型问题 |
|---|---|---|
| reference_period | 被统计的时期，如2026年9月 | 9月数据何时才公布？ |
| event_at | 交易、政策行动或新闻所述事件实际发生时刻 | 新闻可能晚于事件发生 |
| published_at | 对目标使用者公开发布的时刻 | 预告时间不等于实际发布 |
| received_at | 本系统第一次收到相应内容的时刻 | 网络、授权和采集会造成延迟 |
| validated_at | 解析、单位和质量检查完成时刻 | 原始字节到达不等于可直接入模 |
| available_at | 对指定下游服务正式可读的时刻 | 已计算但尚未写入在线存储 |
| feature_completed_at | 某次特征快照实际完成时刻 | 特征所用数据时点与完成时点不同 |
| model_ready_at | 指定模型或规则版本可用于服务的时刻 | 训练完成不一定已经部署 |
| decision_at | 状态识别或预警决策发出的时刻 | 必须晚于所需产物就绪 |

“系统可用”是相对于消费者定义的：数据在原始存储中存在，但对预警服务尚不可读，不能称作对该服务已经可用。

宏观统计参考期通常是区间，不能强行当作一个事件时刻。预测、日程预告还可能描述未来时期；它们今天就可发布，因此不能对所有数据机械要求“参考期结束早于发布时间”。对于已实现的月度统计，应另设对应的数据契约。

本章实验只研究已经结束月份的人工统计数，明确采用：

```math
t_{\mathrm{pub}}\leq t_{\mathrm{recv}}\leq t_{\mathrm{ready}}.
```

这是一套教学时钟协议。真实系统的不同机器可能存在时钟偏差；若日志违反顺序，应先核查时钟、字段定义和采集链路，而不是自动修改时间戳使其“看起来正确”。

### 20.1.2 发布时间为什么不能替代获取时间

假设一份报告在09:30:00公开发布，采集器09:30:02收到，解析和质量检查09:30:05完成，特征09:30:07完成。

若研究的是“市场参与者理论上从何时能看到公告”，09:30:00可能是合适的公开信息边界。

若研究的是“本平台09:30:03的预警是否可实现”，报告仍未成为合格输入。把发布时间直接填入available_at，相当于删除了本系统真实存在的延迟。

**公开信息集（Public Information Set）**与**系统可用信息集（System-Available Information Set）**必须分别定义。在只接收公开数据、无预先授权内容的实验设定下，系统通常只能取得公开信息的一部分；真实研究还须注明具体数据许可和访问渠道。

下载历史数据库时，下载时间是真实存在的；过去的系统接收时间却未必存在。不能在今天下载后，把每条数据的接收时间伪造为当年的发布时间。

有三种诚实做法：

- 有当时日志：使用日志重放。
- 有历史发布版本但无接收日志：使用明确的延迟假设，称为因果离线重建。
- 只有最新修订值：限制为事后分析，或明确数据限制，不声称已完成历史PIT验证。

### 20.1.3 可用时间沿依赖图传播

**数据血缘（Data Lineage）**记录某个结果依赖哪些输入、代码、配置和模型。把依赖关系画成**有向无环图（Directed Acyclic Graph，DAG）**，可以推导产物最早何时能够完成。

设节点 $v$ 依赖集合 $D(v)$ ，每个父节点的可用时刻为 $a_u$ 。节点自身资源和程序准备时刻为 $r_v$ ，运算及发布耗时为非负数 $c_v$ 。假设所有父节点可以并行准备、节点必须等全部父节点就绪，则：

```math
s_v=\max\left(r_v,\max_{u\in D(v)}a_u\right),
\qquad
a_v=s_v+c_v.
```

推导如下。

第一，任一父节点未就绪，节点就不能读取完整输入，所以启动时间至少不早于所有父节点可用时间的最大值。

第二，资源或相应代码版本尚未准备好，也不能启动，所以还要与自身准备时刻取最大值。

第三，启动不等于完成，因此再加计算和发布耗时。

这是确定性教学模型。生产中排队、重试和动态调度会使实际耗时变化；应记录实际完成时间，并用该递推给出一致性检查和最早完成的下界。

例如行情特征在第71秒完成、宏观特征第75秒完成、模型第90秒就绪，融合推理耗时2秒，则：

```math
a_{\mathrm{prediction}}=\max(71,75,90)+2=92.
```

不能因为全部原始数据在第70秒前已经收到，就把预测结果标为第70秒可用。

注意，多个并行分支的等待取最大值；同一串行路径上的耗时才相加。把所有节点耗时简单求和，会高估并行流水线的完成时间。

### 20.1.4 信息集、适应性与非前视

第7章用**信息流（Filtration）**表示随时间增加的信息。现在把它落实到版本数据。

记 $R_t$ 为截至 $t$ 已经可用的全部记录，包括原始版本、修订、撤回、质量标记和运行配置。可写：

```math
\mathcal F_t=\sigma(R_t),
\qquad
\mathcal F_s\subseteq\mathcal F_t\quad(s\leq t).
```

$\sigma(R_t)$ 表示这些记录所生成的信息集合。这里不要求初学者立刻掌握测度论细节，关键是理解：做决策所用的事实和参数应当能由当时记录确定。

输出 $Y_t$ **适应于（Adapted to）**该信息流，意味着它只依赖 $\mathcal F_t$ 中可用的内容：

```math
Y_t=f_t(R_t,\theta_t).
```

其中 $\theta_t$ 是当时已可用的模型、规则或配置。即使输入数据满足PIT，如果 $\theta_t$ 是用未来数据训练、调参或选择出来的，整体仍然前视。

信息的积累与当前数值的变化并不矛盾。修订发布后，系统既知道旧值也知道新值，只是“当前推荐使用值”变了。若直接覆盖旧值，才丢掉了重建历史信息集所需的证据。

**前视偏差（Look-ahead Bias）**是使用当时尚不可得的信息而造成的研究或评估偏差。它不必表现为直接把未来收益放入特征；最新复权因子、后来的行业分类、事后修订GDP、今天训练的文本编码器，都可能成为入口。

### 20.1.5 时间精度与时钟不确定性

若一个数据源只提供发布日期，不能把它无条件解释为当天00:00已可用。日期级信息不足以证明分钟级可用性。

假设真实可用时刻仅能确定在区间内：

```math
a\in[a^-,a^+].
```

要保证在决策时刻 $t$ 使用该数据不会提前，充分的保守条件是：

```math
a^+\leq t.
```

如果 $a^-\leq t\lt a^+$ ，结论应是“可用性不确定”，而不是“肯定可用”。

同理，两个机器时钟的误差上界分别为 $\epsilon_a,\epsilon_t$ 。日志记录的可用时刻与决策时刻为 $\widehat a,\widehat t$ ，则一个保守条件是：

```math
\widehat a+\epsilon_a
\leq
\widehat t-\epsilon_t.
```

左侧取可用时刻最晚的可能值，右侧取决策时刻最早的可能值，因而任何允许误差组合都不破坏顺序。

若同一时钟分辨率内发生多次提交，应进一步保存单调序号、日志位置或一致性快照标识。两个相同的秒级时间戳，并不能证明读取时已经看到写入。

FRED的实时期间参数使用日期，且其区间包含起止日期。这是接口自己的约定；它不能直接提供本平台毫秒级接收时间，也不能不经转换就套用本书的半开区间设计。[FRED实时期间说明](https://fred.stlouisfed.org/docs/api/fred/realtime_period.html)

## 20.2 宏观首次发布、修订批次与双时间模型

### 20.2.1 宏观数据不是“月份到一个数”的永久映射

**数据版本或历史批次（Vintage）**表示某个历史时点可获得的一组统计值。一个批次可能同时：

- 发布新月份的首次值；
- 修改前几个月的值；
- 修改季节调整参数；
- 变更基期或统计方法；
- 撤回此前发布的值。

因而必须区分“统计期”“单条观测的修订号”和“整批发布的批次号”。一个批次可以修改多个统计期；不同统计期的修订次数也可能不同。

真实案例：国家统计局2025年12月26日发布2024年GDP最终核实结果，现价总量比初步核算数减少1018亿元，而不变价增速仍为5.0%。这个案例说明总量修订和增长率修订不是同一件事；这里不据此推断任何资产价格反应。[国家统计局原公告及核算说明](https://www.stats.gov.cn/sj/zxfbhjd/202512/t20251226_1962144.html)

费城联储的实时宏观数据库以历史批次保存时间序列，并为部分指标提供首次、第二次和第三次发布值。它为研究修订影响提供材料，但不是本平台当年运行日志的替代品。[Real-Time Data Set for Macroeconomists](https://www.philadelphiafed.org/surveys-and-data/real-time-data-research/real-time-data-set-for-macroeconomists)

### 20.2.2 两个时间轴分别回答什么

**有效时间（Valid Time）**回答：“这条事实适用于现实世界的哪段时间？”

**事务时间（Transaction Time）**回答：“数据库在什么时间段保存或认可这条记录？”

同时保留两条时间轴的模型称为**双时间模型（Bitemporal Model）**。这是时态数据库的基本概念；Snodgrass教材第2章与第10章系统讨论了相关定义和查询。[作者提供的教材入口](https://www2.cs.arizona.edu/~rts/publications.html)

金融场景还会单独记录“来源发布知识时间”和“下游服务可用时间”。它们与数据库事务时间并非天然相同。今天向数据库导入一份2020年的公告，事务发生在今天，公告发布却在2020年。

因此本书使用“业务有效轴”和“指定消费者的知识轴”解释PIT；在数据库中分别保存这些业务时间与真实写入审计时间，不能用字段名相似来代替语义确认。

一般区间表可以表示为：

```text
entity_id, value,
valid_from, valid_to,
known_from, known_to,
source_version, receipt_id
```

若采用左闭右开区间，查询“在知识时刻 $k$ 看来，业务时刻 $v$ 的值”要求：

```math
v_{\mathrm{from}}\leq v<v_{\mathrm{to}},
\qquad
k_{\mathrm{from}}\leq k<k_{\mathrm{to}}.
```

两个条件是“同时成立”，不是二选一。

### 20.2.3 一个双时间更正案例

假设某合约乘数在10月1日起实际适用的值，应当是20；系统最初误登记为10，直到10月5日才收到更正。

为了聚焦时间语义，暂不讨论10月1日前的记录。

| 值 | 业务有效区间 | 系统认可区间 |
|---|---|---|
| 10 | [10月1日，无穷远) | [10月1日，10月5日) |
| 20 | [10月1日，无穷远) | [10月5日，无穷远) |

于是：

- 业务时刻10月3日、知识时刻10月4日，查询得到10。
- 同一业务时刻、知识时刻10月6日，查询得到20。
- 知识时刻恰为10月5日，在本例的端点约定下使用20。

第一种结果重建的是“当时系统相信什么”，不是声称错误乘数符合真实合约。第二种结果重建的是“今天如何更正过去”。

若10月5日的更正只影响10月1—3日，则还需按业务边界拆分区间；不能把10月4日以后的有效事实一起覆盖。

SQL Server的系统版本表能够保存数据库修改历史，但其系统期间起点按事务开始时间记录。这不自动等于数据发布、事务提交可见或预警服务可读时间；金融PIT仍需单独建模这些时刻。[Microsoft系统版本表说明](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal/overview?view=sql-server-ver17)

### 20.2.4 月度统计的简化双轴表示

本章实验不实现任意有效区间拆分，而使用固定月度统计期：

```text
(series, period, revision, value, status,
 published, received, ready)
```

这里period承担“数据描述哪个月份”的业务轴，ready承担模拟消费者的知识轴。它是适用于月度观测的版本账本，不是完整通用双时间数据库。

规定同一来源、同一指标、同一统计期中，revision是明确具有优先顺序的整数。真实来源如果使用修订链接或批次标识，应由适配器建立可靠顺序；不能按字符串字典序猜测v10和v2，也不能把到达先后当作修订新旧。

本章只有一个固定来源。扩展为多个来源时，应把source加入版本键，并明确主来源、备用来源及切换策略；不能把供应商A的修订号3与供应商B的修订号2直接比较。

### 20.2.5 修订误差如何改变统计结论

设同一统计期的首次值为 $x_t^{(1)}$ ，在预先规定的评估批次中取得的较后值为 $x_t^{(L)}$ 。定义修订量：

```math
d_t=x_t^{(L)}-x_t^{(1)}.
```

注意 $L$ 是明确指定的后续版本，不是假定永远不会再改的“终极真值”。

对一个已经冻结的预测 $\widehat x_t$ ，首次发布口径的误差为：

```math
e_t^{(1)}=\widehat x_t-x_t^{(1)}.
```

后续版本口径的误差为：

```math
e_t^{(L)}
=\widehat x_t-x_t^{(L)}
=\widehat x_t-x_t^{(1)}-d_t
=e_t^{(1)}-d_t.
```

平方并取期望：

```math
\begin{aligned}
\left(e_t^{(L)}\right)^2
&=\left(e_t^{(1)}\right)^2-2e_t^{(1)}d_t+d_t^2,\\[0pt]
\mathrm E\left[\left(e_t^{(L)}\right)^2\right]
&=\mathrm E\left[\left(e_t^{(1)}\right)^2\right]
-2\mathrm E[e_t^{(1)}d_t]+\mathrm E[d_t^2].
\end{aligned}
```

因此更换评价版本后，均方误差可能增加，也可能减小，取决于交叉项。不能断言使用最新修订值一定让预测“更准”或“一定更差”。

单点例子：预测2.4，首次值2.3，后续值2.7。

```math
e^{(1)}=0.1,\quad d=0.4,\quad e^{(L)}=-0.3.
```

```math
0.1^2-2(0.1)(0.4)+0.4^2
=0.01-0.08+0.16
=0.09.
```

这与后续口径的平方误差 $(-0.3)^2$ 一致。

这里的平方误差分析只研究“评价目标变化”。如果连训练输入和模型选择也跟着更换版本，改变的就不止目标，必须分别控制实验条件。

### 20.2.6 新信息修订与噪声修订

为理解修订来源，可以比较两个理想化模型。它们是分析假设，不能在没有检验时认定真实统计满足其中之一。

**新信息模型（News Model）**：首次值等于当时对后续目标的条件期望。

```math
x^{(1)}=\mathrm E[x^{(L)}\mid\mathcal I_1],
\qquad
d=x^{(L)}-x^{(1)}.
```

对首次信息集取条件期望：

```math
\mathrm E[d\mid\mathcal I_1]
=\mathrm E[x^{(L)}\mid\mathcal I_1]-x^{(1)}
=0.
```

若二阶矩存在，首次值属于当时信息集，所以：

```math
\mathrm E[x^{(1)}d]
=\mathrm E\left[x^{(1)}\mathrm E[d\mid\mathcal I_1]\right]
=0.
```

再由 $\mathrm E[d]=0$ 得到两者协方差为0。此时修订代表首次发布时未能预知的新信息。

**噪声模型（Noise Model）**：首次值等于后续目标加测量噪声：

```math
x^{(1)}=x^{(L)}+\eta,\qquad
\mathrm E[\eta]=0,\qquad
\mathrm{Cov}(x^{(L)},\eta)=0.
```

则 $d=-\eta$ ，所以：

```math
\mathrm{Cov}(d,x^{(1)})
=\mathrm{Cov}(-\eta,x^{(L)}+\eta)
=-\mathrm{Var}(\eta).
```

首次值偏高时，修订倾向于向下。两个模型产生不同的可检验相关结构，但现实修订可以混合新信息、测量误差、方法变更和基期调整。短样本、序列相关以及后续版本仍有误差，都会影响检验。

对监控平台来说，修订量可以成为单独的特征；它只能在修订已可用后进入系统，不能回填到首次发布的历史状态中。

## 20.3 截至时点查询、历史重放与前视偏差审计

### 20.3.1 先筛可见版本，再选最新版本

设某个指标统计期的版本集合为 $V_p$ ，版本 $j$ 的可用时刻为 $a_j$ ，修订优先级为 $r_j$ 。

截至时点 $\tau$ ，先定义可见集合：

```math
V_p(\tau)=\lbrace j\in V_p:a_j\leq\tau\rbrace.
```

若集合非空，选择：

```math
j^*(p,\tau)
=\arg\max_{j\in V_p(\tau)}r_j.
```

空集合对应缺失，不能猜测一个值。

为什么顺序不能交换？设同一统计期有v1、v2：

| 版本 | ready | 值 |
|---|---:|---:|
| v1 | 15 | 230 |
| v2 | 80 | 270 |

在第20秒，先筛选得到仅有v1，再取最大修订号得到v1。

如果先在全表中取最大修订号，得到v2；然后发现v2尚不可用而删除，最终变成空结果。此时并没有直接读到未来值，但却错误地用未来版本的存在抹掉了历史可用值。

令 $F_\tau$ 表示可见性筛选， $L$ 表示按键取最新版本，则一般有：

```math
L(F_\tau(V))\neq F_\tau(L(V)).
```

这既是PIT问题，也是关系查询的运算顺序问题。

本章代码使用公共表表达式和窗口函数：第一层WHERE筛可用，第二层ROW_NUMBER按指标及统计期分组，最后取序号1。ROW_NUMBER不是金融模型，只是为每个分组排序编号。[SQLite窗口函数文档](https://www.sqlite.org/windowfunctions.html)

### 20.3.2 最新统计期与最新收到的发布不是一回事

在第50秒，10月首次值已经可用。第80秒收到9月修订值。

“最新发布事件”确实变成9月修订；但“最新已发布月份”仍是10月。

正确步骤是：

1. 对每个统计期分别恢复当时最新版本。
2. 再按任务选择某个统计期，或最新统计期。
3. 保留实际选中的统计期、版本号与可用时间。

若把“最后一条宏观消息”直接当作“当前宏观水平”，旧月份修订就会使看板倒退到旧月份。

不同任务可以采用不同规则。例如修订监控看“最新修订事件”，经济现状卡片看“最新统计期”，同比增速计算则需要两个指定统计期。规则名称和返回字段应明确区分。

### 20.3.3 撤回必须先成为版本，再解释缺失

**撤回记录（Retraction）**说明某个此前发布的事实已不应继续使用。可用一个带WITHDRAWN状态、数值为空的新版本表示，常称为墓碑记录。

错误做法：先删除所有空值或WITHDRAWN行，再选择最新版本。这样撤回记录消失，旧版本反而重新出现。

正确做法：包括撤回记录在内选择最新可见版本，然后解释其状态。若最新版本是撤回，则该统计期当前不可用。

是否允许回退到上一个月，是另一个业务决定。本章选择不自动回退；若产品允许展示旧月份，必须标注“旧期数据”，不能伪装为当前月份已恢复。

同理，撤回后再次发布，要新增后续版本，不能删除撤回记录。历史查询仍应能看到“在某一段时间内该数据已撤回”。

### 20.3.4 批次一致性与同比特征

同一批发布可能同时修订当期和去年同期。若分子读到新批次、分母仍是旧批次，结果可能不属于任何真实发布版本。

设某个一致历史快照下，当前月水平为 $x_t^{(\tau)}$ ，去年同月水平为 $x_{t-12}^{(\tau)}$ ，同比为：

```math
g_t^{(\tau)}
=\frac{x_t^{(\tau)}}{x_{t-12}^{(\tau)}}-1.
```

这里同一个 $\tau$ 表示共同的知识截面，并不要求两个值具有相同的局部修订号。

例：旧快照是110和100，同比增长10%；新批次同时修订为111和105，则：

```math
g_{\mathrm{new}}=\frac{111}{105}-1
\approx0.057143.
```

若读到新分子111和旧分母100，会得到11%，这一组合既不是旧快照的10%，也不是新快照的约5.7143%。

解决方案包括：把一批记录在单个事务中提交；在批次完整性检查后统一标为可用；或查询同一个版本化快照。跨多个在线存储时，仅让查询使用相同墙上时间，仍未必能保证一致可见性。

本章只有五条独立人工版本记录，没有实现整批提交协调；在工程扩展中应增加release_batch_id、batch_ready_at和快照标识。

### 20.3.5 三种历史研究视图

| 视图 | 数据与时间依据 | 能回答的问题 |
|---|---|---|
| 原样历史重放 | 当时实际接收、处理、服务日志及当时模型 | 本系统当时实际输出了什么？ |
| 因果离线重建 | 历史发布版本、明确的延迟与运行假设 | 在这些假设下，当时可能算出什么？ |
| 最新修订研究 | 今天已知的较新数据与口径 | 用目前知识怎样解释过去？ |

三者都可能有研究价值，但证据强度和问题不同。

用今天改进的算法重算过去，即使每个时点仅使用可见数据，也不是原样重放；它是新的离线实验。若算法结构本身是在观察完整测试期后选出的，还存在研究选择偏差。

最新修订研究也不必然“错误”。它适合研究较稳定口径下的经济关系，只是不能直接宣称其输入当时能够支持实时预警。

### 20.3.6 训练集的版本策略也要声明

在训练截止时点 $T$ ，对于历史样本时点 $t\lt T$ ，有两种常见且不同的特征构造策略。

**决策时点版本策略**：每条历史样本使用当时可用值 $x_t^{(t)}$ 。这更接近模型将来在首次发布或实时快照上工作的输入分布。

**训练时点版本策略**：全部历史样本使用截至训练时点可得的值 $x_t^{(T)}$ 。这些值在训练时确实已经知道，因而不自动构成对 $T$ 之后测试期的前视；但可能造成训练输入较“干净”、线上首次值较嘈杂的分布差异。

真正明显泄漏的是，在模拟截止 $T$ 的训练中使用 $T$ 之后才发布的修订，或在整个测试期结束后统一回填最新值。

监督标签也有自己的可用时间。若标签定义为未来 $h$ 期结果，并在期末之后延迟 $\ell$ 才获得，则样本进入训练至少要求：

```math
t+h+\ell\leq T.
```

不能只用 $t\lt T$ 判断其可训练性。训练、验证和测试的标签重叠处理会在后续时间序列交叉验证章节展开。

标准化均值、缺失填补规则、PCA载荷、特征选择、状态阈值和文本模型，都属于模型依赖，必须遵循相同的训练边界。

### 20.3.7 前缀不变性：一个可自动检查的必要条件

**前缀不变性（Prefix Invariance）**指：如果两份数据在截止 $\tau$ 前的可用记录完全相同，那么使用固定算法和配置产生的截至 $\tau$ 输出应当一致。

记 $D|_\tau$ 表示数据集按可用时间截出的前缀。则希望：

```math
D|_\tau=D'|_\tau
\quad\Longrightarrow\quad
A(D;\tau)=A(D';\tau).
```

证明思路很直接：一个因果确定性程序只能读取前缀；前缀相同、程序和配置相同，每一步读取及计算就相同。随机程序还应固定随机状态，或比较其条件输出分布。

实际测试可以增加未来修订、把未来价格改成极端数值，再检查历史结果是否保持不变。

但通过测试不等于证明整个系统绝无泄漏：

- 程序可能依赖测试没有覆盖的另一张表。
- 时间戳本身可能被错误回填。
- 模型文件可能已包含未来信息。
- 修改未来数据没有改变数值输出，可能只是模型对该输入不敏感。
- 测试样本未覆盖的路径仍可能出错。

因此应把反例测试与输入血缘、版本冻结、查询审查和运行记录结合。PIT是端到端属性，不是给一张表加available_at列就自动获得的属性。

### 20.4.3 完整主程序

```python
"""Synthetic PIT ledger. Standard library only; no live market connection."""
from dataclasses import asdict, dataclass
from datetime import datetime, timezone
from pathlib import Path
import hashlib
import json
import platform
import sqlite3

BASE = "2026-11-02T00:00:00+00:00"
SCHEMA = """
CREATE TABLE vintage (
    id TEXT PRIMARY KEY,
    series TEXT NOT NULL,
    period TEXT NOT NULL,
    revision INTEGER NOT NULL CHECK(revision > 0),
    value INTEGER,
    status TEXT NOT NULL CHECK(status IN ('OK','WITHDRAWN')),
    published INTEGER NOT NULL,
    received INTEGER NOT NULL,
    ready INTEGER NOT NULL,
    UNIQUE(series, period, revision),
    CHECK(published >= 0 AND published <= received AND received <= ready),
    CHECK((status='OK' AND value IS NOT NULL) OR
          (status='WITHDRAWN' AND value IS NULL))
) STRICT;
CREATE INDEX visible_idx ON vintage(series, ready, period, revision);
CREATE TRIGGER no_update BEFORE UPDATE ON vintage
BEGIN SELECT RAISE(ABORT, 'append only'); END;
CREATE TRIGGER no_delete BEFORE DELETE ON vintage
BEGIN SELECT RAISE(ABORT, 'append only'); END;
"""
PIT_SQL = """
WITH visible AS (
    SELECT * FROM vintage WHERE series=? AND ready<=?
), ranked AS (
    SELECT *, ROW_NUMBER() OVER (
        PARTITION BY series, period ORDER BY revision DESC
    ) AS rn FROM visible
)
SELECT id, series, period, revision, value, status, published, received, ready
FROM ranked WHERE rn=1 ORDER BY period
"""


@dataclass(frozen=True)
class Vintage:
    id: str
    series: str
    period: str
    revision: int
    value: int | None
    status: str
    published: int
    received: int
    ready: int


def new_db(path=":memory:"):
    db = sqlite3.connect(path)
    db.row_factory = sqlite3.Row
    db.executescript(SCHEMA)
    return db


def append(db, v):
    """Input is an already validated first-acceptance record, not a delivery."""
    parsed = datetime.strptime(v.period, "%Y-%m")
    if parsed.strftime("%Y-%m") != v.period:
        raise ValueError("period must be canonical YYYY-MM")
    for name in ("revision", "published", "received", "ready"):
        if type(getattr(v, name)) is not int:
            raise ValueError("integer required: " + name)
    if v.value is not None and type(v.value) is not int:
        raise ValueError("value must be integer or None")
    old = db.execute(
        "SELECT * FROM vintage WHERE series=? AND period=? AND revision=?",
        (v.series, v.period, v.revision)
    ).fetchone()
    if old is not None:
        if dict(old) == asdict(v):
            return "DUPLICATE"
        raise ValueError("conflicting normalized version")
    with db:
        db.execute("INSERT INTO vintage VALUES (?,?,?,?,?,?,?,?,?)",
                   tuple(asdict(v).values()))
    return "ACCEPTED"


def asof(db, cutoff, series="CPI_DEMO"):
    if type(cutoff) is not int or cutoff < 0:
        raise ValueError("cutoff must be nonnegative integer seconds")
    return [dict(r) for r in db.execute(PIT_SQL, (series, cutoff))]


def period_at(db, cutoff, period):
    return next((r for r in asof(db, cutoff) if r["period"] == period), None)


def current_at(db, cutoff):
    rows = asof(db, cutoff)
    # A withdrawn newest period remains withdrawn; do not resurrect older data.
    return rows[-1] if rows else None


def freeze_feature(db, cutoff, completed):
    if type(completed) is not int or completed < cutoff:
        raise ValueError("completion precedes snapshot")
    row = current_at(db, cutoff)
    return {"cutoff": cutoff, "completed": completed, "input": row,
            "feature_code": "latest-period-v1"}


def infer(feature, rule, decision):
    if type(decision) is not int:
        raise ValueError("decision must be integer")
    if decision < max(feature["completed"], rule["ready"]):
        raise ValueError("feature or rule not yet available")
    row = feature["input"]
    label = "UNKNOWN"
    if row is not None and row["status"] == "OK":
        label = "HIGH" if row["value"] >= rule["threshold"] else "LOW"
    return {"decision": decision, "label": label, "rule": dict(rule),
            "feature": feature}


def samples():
    return [
        Vintage("sep-v1", "CPI_DEMO", "2026-09", 1, 230, "OK", 10, 12, 15),
        Vintage("oct-v1", "CPI_DEMO", "2026-10", 1, 240, "OK", 40, 42, 50),
        Vintage("sep-v2", "CPI_DEMO", "2026-09", 2, 270, "OK", 60, 65, 80),
        Vintage("oct-v2", "CPI_DEMO", "2026-10", 2, None, "WITHDRAWN",
                100, 105, 110),
        Vintage("oct-v3", "CPI_DEMO", "2026-10", 3, 260, "OK", 120, 125, 130),
    ]


def run(db):
    events = samples()
    for v in events:
        append(db, v)
    cuts = [12, 15, 50, 70, 80, 110, 130]
    views = {str(c): asof(db, c) for c in cuts}
    # Deliberately WRONG: rank all versions, then filter readiness.
    wrong = db.execute("""
        WITH ranked AS (
          SELECT *, ROW_NUMBER() OVER (
            PARTITION BY series, period ORDER BY revision DESC
          ) AS rn FROM vintage
        )
        SELECT id FROM ranked WHERE rn=1 AND ready<=20
    """).fetchall()
    rule = {"id": "rule-v2", "ready": 90, "threshold": 250}
    frozen = freeze_feature(db, 70, 75)
    try:
        infer(frozen, rule, 80)
    except ValueError as exc:
        rejected = str(exc)
    else:
        raise AssertionError("future rule was accepted")
    return {
        "data_kind": "SYNTHETIC", "base_utc": BASE,
        "unit": "percent scaled by 100", "inputs": [asdict(v) for v in events],
        "snapshots": views, "wrong_rank_first_at_20": [r["id"] for r in wrong],
        "rejected_at_80": rejected,
        "prediction_at_90": infer(frozen, rule, 90),
        "prediction_at_135": infer(freeze_feature(db, 130, 132), rule, 135),
        "september_comparison": [
            {"cutoff": c, "pit": period_at(db, c, "2026-09")["value"],
             "restated": period_at(db, 130, "2026-09")["value"]}
            for c in (20, 70)
        ]
    }


def digest(path):
    return hashlib.sha256(path.read_bytes()).hexdigest()


def main():
    stamp = datetime.now(timezone.utc).strftime("%Y%m%dT%H%M%S_%fZ")
    out = Path(__file__).parent / "runs" / ("run_" + stamp)
    out.mkdir(parents=True)
    db = new_db(out / "pit.db")
    try:
        result = run(db)
        integrity = db.execute("PRAGMA integrity_check").fetchone()[0]
    finally:
        db.close()
    target = out / "results.json"
    target.write_text(json.dumps(result, ensure_ascii=False, indent=2),
                      encoding="utf-8")
    manifest = {
        "data_kind": "SYNTHETIC", "python": platform.python_version(),
        "sqlite": sqlite3.sqlite_version, "integrity_check": integrity,
        "program_sha256": digest(Path(__file__)),
        "results_sha256": digest(target), "db_sha256": digest(out / "pit.db"),
        "policy": "ready<=cutoff; revision per period; then newest period"
    }
    (out / "manifest.json").write_text(
        json.dumps(manifest, ensure_ascii=False, indent=2), encoding="utf-8")
    print(json.dumps({"run_dir": str(out), **manifest}, ensure_ascii=False))


if __name__ == "__main__":
    main()
```

### 20.4.4 核心机制逐步解释

**第一，数据库约束保护结构。**

复合唯一键把同一指标、同一月份、同一修订号约束为一个版本。状态约束要求正常值非空、撤回值为空。时间约束要求发布不晚于接收，接收不晚于就绪。禁止UPDATE和DELETE的触发器阻止普通应用路径覆盖历史。

输入月份必须是规范的YYYY-MM。这样按字符串排序才与月份先后相同；若混入2026-9，字典序就不能可靠表示日期顺序。

**第二，筛选顺序保护历史。**

PIT_SQL先保留ready不晚于cutoff的记录，再在每个月份内按revision降序编号。约束保证ready不早于published和received，所以该查询不必重复写另外两个时间条件。

这个推论依赖约束真实成立。若ready的语义改了，或从外部载入未经检查的数据，不能继续照搬这一简化。

**第三，业务选择与版本选择分开。**

asof返回每个统计期的可见最新版本；period_at查询指定月份；current_at再取最新月份。撤回记录不提前删除，所以不会复活旧值。

**第四，冻结特征与门控推理。**

freeze_feature保留特征截止、完成时刻、输入版本内容和特征代码标识。infer检查特征与规则均已就绪，结果同时记录规则内容和输入快照。

这里规则是事先手工指定的2.50%阈值，HIGH/LOW仅表示该人工指标高于或低于阈值；不等同于真实通胀状态，更不等同于牛熊市场。UNKNOWN表示当前没有可用正常值。

为了把关注点放在可用性，代码假定推理本身耗时为0。生产服务应记录请求、推理完成及发布时刻，把实测耗时加到依赖链中。

Python字典不是不可变审计存储。代码通过查询产生新字典并最终序列化保存，但不防止调用方主动改写传入的feature。因此生产中还需不可变产物标识、内容哈希、写入权限与持久决策记录。

| 110 | v2，2.70% | v2，撤回 | 10月不可用 |
| 130 | v2，2.70% | v3，2.60% | 10月2.60% |

第70秒，9月修订已经发布并收到，但直到80秒才完成处理，所以查询仍使用2.30%。

在第20秒，错误的“先取全表最大修订号再筛ready”查询返回空，而正确查询返回sep-v1。这说明历史缺失也可能由前视查询制造。

第70秒冻结的当前特征为10月2.40%，第75秒完成。rule-v2第90秒就绪：

- 第80秒推理被拒绝。
- 第90秒使用该冻结特征，得到LOW，并保留输入oct-v1。
- 第130秒冻结、132秒完成的新特征，在135秒推理得到HIGH，输入为oct-v3的2.60%。

第20秒与第70秒的9月PIT值均为2.30%；若错误使用第130秒所见修订值，则都变成2.70%。以2.50%为阈值，两次分类都会由低变高。这里只演示版本改变分类，不能称为预测准确率下降，因为没有设置独立的真实状态标签。

### 20.4.6 测试应验证语义，而不只是程序能启动

12项测试覆盖：

1. 可用时间14/15秒的边界。
2. 已接收但未就绪的修订。
3. 先筛选与先排序的反例。
4. 旧月份修订不替换最新月份。
5. 撤回不复活旧值，推理输出UNKNOWN。
6. 重新发布恢复可用值。
7. 新增并大幅修改未来数据，历史前缀不变。
8. 按相反物理顺序导入完整账本，查询相同。
9. 完全重复幂等、同版本冲突拒绝。
10. 非规范月份、错误类型、时间倒置与覆盖删除被拒绝。
11. 特征与规则就绪门控、冻结输入版本。
12. 完整重放的输出一致性。

“导入顺序不影响历史查询”只适用于每条记录携带可信、已冻结历史可用时间的重建。真实在线接入不能允许客户端随意提交ready=过去，从而把今天收到的信息插入昨天的信息集。

### 20.4.7 工程扩展、性能与常见失误

本例每次截至查询可能扫描该指标的多条历史版本，再进行分组排序。若有 $N$ 条候选版本，朴素处理可具有 $O(N\log N)$ 的排序成本；具体执行计划和索引利用取决于数据库。不能因为建了一个索引就宣称查询一定是常数时间。

可选设计如下：

| 设计 | 优点 | 代价与适用边界 |
|---|---|---|
| 追加式版本账本加窗口查询 | 易审计，能重建任意知识截面 | 历史版本多时查询较重 |
| 显式知识区间表 | 截面查询直观 | 区间关闭、拆分及并发约束复杂 |
| 周期快照加增量日志 | 重放距离短，适合大历史库 | 快照版本、增量完整性和恢复需额外管理 |
| 当前视图加完整历史账本 | 在线读快，历史留证完整 | 必须保证两份视图更新一致 |
| 数据库原生系统版本功能 | 自动保留数据库修改历史 | 不替代来源发布、服务可用及业务有效时间 |

对大量滚动历史时点，可按ready排序增量维护“每个统计期的最高可见修订”，避免每个时点从头扫描。但迟到旧版本、撤回和重复都应按版本优先级处理，不能只保留最后到达的一行。

本例没有实现：

- 原始网络消息与授权审计；
- 任意有效区间的完整双时间更新；
- 多来源融合、整批原子可见；
- 跨机器时钟校准和一致性快照；
- Kafka重放、分布式故障恢复和服务发布；
- 学习型模型训练、真实宏观数据接入与预测绩效评估。

此外，本例每次运行新建数据库，程序中途失败不会自动从中断点续跑；SQLite单次事务能力不能被表述为整个平台已经具备故障恢复。

这些不是省略PIT原则的理由，而是后续分布式与平台工程章节应接续实现的边界。

## 本章总结

PIT安全保护的是“在某个时刻能够知道什么、能够算出什么”。统计期、发布时间、接收时间和服务可用时间分别回答不同问题。

宏观版本选择必须先筛可见，再在各统计期内取最新修订；最新月份、最新发布事件和最新修订值是不同对象。撤回也是版本，不能先删空值再选版本。

双时间模型把业务有效与知识历史分开。历史重放要恢复当时证据，离线重建要公开假设，最新修订研究要明确事后视角。模型、配置和特征产物也必须满足时间约束。

本章实验为整个平台提供可验证的“信息入口规则”；后续特征工程将在这个规则之上计算技术指标和宏观因子。

## 详细参考答案

### 题1

统计期是9月，是数据描述的月份；公开发布为11月2日10:00；接收为10:00:02；验证完成为10:00:06；对依赖在线存储的预警服务，可用时刻是10:00:08。

10:00:04不能作为合格输入。它虽然已收到，但检查和在线发布均未完成。若另一业务直接消费原始消息，其可用性应另订契约，不能把两种消费者混为一谈。

### 题2

等待三个并行条件全部满足：

```math
t_{\mathrm{start}}=\max(71,75,90)=90.
```

推理与发布串行执行：

```math
t_{\mathrm{display}}=90+2+1=93.
```

71、75、90是相对同一原点的完成时刻，不是三段串行耗时；相加既违反依赖结构，也把起点重复计算了。

### 题3

20秒与70秒仅v1满足ready不晚于截止；80秒开始v1、v2都满足，revision较大的v2胜出。

先取全表最大revision会提前丢掉v1，之后过滤v2时得到空结果。未来版本未被直接显示，但它仍影响了历史结果，违反前缀不变性。

### 题4

知识时刻10月4日落在旧记录区间，结果10；10月5日与6日落在新记录区间，结果20。恰在5日不再选旧记录，因为旧区间右端开放。

若更正只影响10月1—3日（含3日整天），可以把业务区间写为[10月1日，10月4日)和[10月4日，无穷远)。后者保留原本正确的值，前者按知识轴保存更正前后版本。应明确“3日”是整日还是某个精确时刻，不能让自然语言代替端点契约。

### 题5

首次误差：

```math
e^{(1)}=3.0-2.5=0.5,\qquad
\left(e^{(1)}\right)^2=0.25.
```

修订量为 $d=2.8-2.5=0.3$ 。后续误差：

```math
e^{(L)}=3.0-2.8=0.2,\qquad
\left(e^{(L)}\right)^2=0.04.
```

分解验证：

```math
0.25-2(0.5)(0.3)+0.3^2
=0.25-0.30+0.09
=0.04.
```

误差减少发生在同一个冻结预测上，只说明目标版本改变后更接近这个预测。它没有比较两种训练策略，更没有证明最新值可以提前用于历史决策。

### 题6

假定变量具有有限二阶矩。新信息模型给出 $\mathrm E[d\mid\mathcal I_1]=0$ 。首次值对 $\mathcal I_1$ 可测，因此：

```math
\mathrm E[x^{(1)}d]
=\mathrm E[x^{(1)}\mathrm E[d\mid\mathcal I_1]]=0.
```

再由全期望公式得到 $\mathrm E[d]=0$ ，所以：

```math
\mathrm{Cov}(x^{(1)},d)
=\mathrm E[x^{(1)}d]-\mathrm E[x^{(1)}]\mathrm E[d]=0.
```

噪声模型中 $d=-\eta$ ，展开协方差，利用目标与噪声不相关：

```math
\mathrm{Cov}(d,x^{(1)})
=-\mathrm{Cov}(\eta,x^{(L)})-\mathrm{Var}(\eta)
=-\mathrm{Var}(\eta).
```

当噪声方差严格为正时结果严格为负；方差为0时为0。注意不相关不等于独立，也不保证小样本估计恰好等于理论值。

### 题7

旧同比是110/100−1=10%；新同比是111/105−1≈5.7143%；混合同比是111/100−1=11%。

方案一：同批次所有记录通过校验后，在一个事务中原子提交，并在提交可见后统一开放。

方案二：先生成不可变快照，消费者按snapshot_id读取分子与分母；只有完整快照才发布可用标记。两种方案都要处理失败批次，不能让不完整批次获得ready标记。

### 题8

筛掉撤回行后，10月v1会重新成为最大可见版本，显示已被撤回的2.40%。

应先选择最新可见版本，返回WITHDRAWN、版本id、撤回时间和空值。若业务允许回退展示9月值，应同时显示统计期2026-09、当前10月状态WITHDRAWN、回退原因及数据年龄；“旧期参考值”与“当前期有效值”必须区分。

### 题9

以下程序可以放在code/ch20目录运行；若在其他工作目录运行，应把该目录加入模块搜索路径。

```python
from pit_lab import append, freeze_feature, infer, new_db, period_at, current_at, samples

db = new_db()
try:
    for row in samples():
        append(db, row)
    assert period_at(db, 70, "2026-09")["value"] == 230
    assert period_at(db, 80, "2026-09")["value"] == 270
    assert current_at(db, 110)["status"] == "WITHDRAWN"
    feature = freeze_feature(db, 70, 75)
    rule = {"id": "rule-v2", "ready": 90, "threshold": 250}
    prediction = infer(feature, rule, 90)
    assert prediction["feature"]["input"]["id"] == "oct-v1"
    assert prediction["label"] == "LOW"
    print("PIT assertions passed")
finally:
```

断言同时检查值、撤回状态和输入血缘。只检查最终标签不够，因为多个错误版本可能恰好得到同一个标签。

### 题10

标签可用条件为：

```math
t+5+1\leq100,
\qquad t\leq94.
```

所以第94天可以，第95天和99天不可以。数据文件中“出现了某个值”不证明现实中当时可获得；提前写入可能来自错误回填或未来信息泄漏，应调查标签生成过程。

若实际业务提供更早的可验证标签，则需要修改原题定义和可用性契约，不能一边保留“延迟1天”的定义一边提前使用。

### 题11

第一种情况，可用时刻最晚为10:00:00.600，决策时刻最早为10:00:00.550。600毫秒不早于550毫秒，不能保证可用在先；但也不能据此证明一定发生了前视，正确结论是顺序不确定。

第二种情况，决策最早为10:00:00.700，已经晚于最晚可用时刻600毫秒，所以在给定误差界内可以保证顺序。

误差界若未经测量或可靠约束，这个结论也只是条件性的。

### 题12

参考请求：

```json
{
  "prediction_id": "demo-alert-90",
  "view": "original_replay",
  "include_lineage": true
}
```

响应应包含决策时间、特征截止与完成时间、具体输入版本、来源和原始接收证据、规则或模型产物标识、可用时间、代码配置哈希、日历和主数据版本、输出类别及解释。

原样重放还应对应当时不可变预测记录；如果只有历史公开版本和假设延迟，view应标为causal_reconstruction，并返回假设清单，不能仍称original_replay。

撤回后，历史已发预警不应被无痕改写。系统可以新增更正说明，关联原预警及撤回版本。用户查询“当时显示”与“现在重算”应得到分别标注的结果。

建议评价标准：

- 时间语义与端点明确：20分。
- 每个输入及模型可追溯：25分。
- 修订、撤回和多批次一致性：20分。
- 前缀不变、边界、冲突和故障测试：20分。
- 接口可运行、查询成本与权限合理：15分。

仅返回一个风险分数、没有输入版本和运行证据的方案，不能算完成PIT审计。
