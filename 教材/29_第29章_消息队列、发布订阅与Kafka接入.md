# 第29章 消息队列、发布订阅与Kafka接入

第28章的账本能回答“当时可见的股价是多少”。现在多接一个服务：看板每分钟刷新一次，审计程序保存每一笔报价，特征程序还会因为模型升级而停机。三个服务各有自己的处理速度。如果接入器逐个调用它们，最慢的一个就决定了下一笔行情什么时候能进来。把行情先追加到一条可重读的日志，接入器只需等待本次写入的确认；各服务自己记录读到了哪里。由此产生一个新的故障窗口：数据库已经写好，消费进度还没提交，进程退出。重启后该从哪里读？

**学习目标。** 先修第26章的背压、第27章的复制与确认，以及第28章的物理版本键。读完后应能画出一个主题的分区与消费组，手算消费位置和恢复时间，区分同一位置重读与来源重复，设计可审计的行情消息，并让 Kafka 消费者按正确顺序提交外部数据库和偏移量。

## 29.1 日志、主题、分区、消费者组与偏移量

**消息队列（message queue）**让生产和处理分开推进。传统工作队列常把一件工作交给一个工作者，成功确认后即可清除。**发布订阅（publish–subscribe）**让多个订阅者各自取得同一项发布。Kafka 的常规消费组建立在**追加日志（append-only log）**上：发布者向日志末尾追加记录，读者保存自己的位置。消费成功后，记录仍可供别的组读取，实际保留范围取决于主题的清理策略。[Apache Kafka 设计文档](https://kafka.apache.org/41/design/design/)

**主题（topic）**是有名称的一类消息。**分区（partition）**是主题内可独立追加和读取的一条日志。**代理节点（broker）**承载分区及副本。记录在分区内有一个**偏移量（offset）**。定位一条记录需要主题、分区和偏移量；归档跨集群或主题可能删除后重建时，还应记录集群和主题实例身份。分区 0 的偏移量 5 与分区 1 的偏移量 5 没有全局先后关系。

**消费者组（consumer group）**共享一套进度，在常规组订阅协议下，一个分区在一次稳定分配中由组内一个成员负责。两个组各自读取全部分区。把审计和特征服务设为不同组，两者可以分别重放；把它们设为同一组，则一个成员可能只见到股票，另一个只见到外汇。若两个分区配三个同组成员，至多两个成员能分到当前主题的分区。成员加入、离开或失去心跳会触发**再均衡（rebalance）**，分区所有权和后续处理随之调整。

### 位置为何要加一

一个分区含偏移量 0、1、2 三条普通记录。下一条追加位置是 3。消费者拉取三条后，其读取位置可以到 3；若只有 0 和 1 的业务效果已经持久化，可安全提交的**下一读取位置**是 2。重启从 2 读，恰好处理第三条。若把“最近完成的偏移量 1”原样提交，下一轮又会读到 1；若把已拉取位置 3 提交，进程此刻退出便会跳过 2。

记分区末端的下一位置为 $E_p$ ，组已提交的下一位置为 $C_p$ 。在本章从零连续编号、无压缩和事务控制记录的日志中，组尚未越过的条数为

```math
L=\sum_p (E_p-C_p).
```

例如末端为 (6,4)，提交位置为 (2,3)，第一分区余 4 条，第二分区余 1 条，合计 5 条。真实 Kafka 的日志压缩可留下偏移量空洞，事务可见性还会改变读者当前可读的边界。运维报表需说明末端取自哪种观测及隔离级别；位置差通常作为积压指标，业务遗漏还要独立对账。

同分区并发处理要跟踪**连续完成前缀**。已分派 10、11、12，完成顺序为 12、10、11，则每次完成后可安全提交的下一位置依次为 10、11、13。只取已完成编号最大值会在第一次完成时越过两条未完成消息。实务中以交付给应用的实际记录序列追踪前缀，遇到合法偏移量空洞时按客户端交付边界推进。

## 29.2 消息键、顺序性、重复与幂等生产

消息的**键（key）**参与路由，值（value）携带正文。行情按资产路由，可以让同一股票的首次报价与后续更正沿同一日志传递。键的字节编码、分区器和分区数都是路由契约的一部分；扩充分区时，常见的哈希取模规则会将部分旧键映射到新分区。迁移期间要保存切换边界或使用明确的路由版本。本章固定两个分区，股票和债券在 0，外汇和黄金在 1，方便手工核对。

分区顺序回答“哪条先追加”。来源事件时间回答“哪笔行情较早发生”。昨天的股票报价今天更正，它会排在今天刚追加的记录后面，但仍修订昨天的事件。消费者需保留第28章的 `event_s`、`revision` 和 `ready_s`；重放到机器上的当前时间另行登记。恢复程序若把旧消息的重放时刻写成首次可用时刻，会改变历史模型可见的数据。

有三种容易混淆的重复：

| 现象 | 判别键 | 对账动作 |
|---|---|---|
| 消费者重启，重读同一位置 | 同组、同主题实例、同分区、同偏移量 | 已有收据且键、载荷一致，返回 REPLAY；原业务效果保留一次 |
| 来源重复发布，获得新偏移量 | 物理位置不同，业务键与规范内容相同 | 保留第二张物理收据，业务版本记作 DUPLICATE |
| 相同业务版本出现不同内容 | 业务键相同、内容不同 | 保留冲突原文并隔离；正式更正应有新版本编号 |

**幂等生产（idempotent production）**使生产者在协议允许的重试中避免把同一批次重复追加。Kafka 利用生产者身份、纪元及分区序列号等信息识别重传。应用程序自己再次调用生产接口、显式发送同一个业务事件时，会形成一次新的发送；消费者仍需要业务版本键。设置 `acks=all` 时，成功确认要求当前同步副本集合满足写入条件；主题的 `min.insync.replicas` 规定可接受写入所需的最少同步副本数。单副本练习能观察确认流程，容忍某台机器丢失需要独立的副本部署。[Kafka 设计](https://kafka.apache.org/41/design/design/) · [生产者配置](https://kafka.apache.org/41/configuration/producer-configs/)

### 两次提交之间发生了什么

设业务效果为 B，组偏移量提交为 C。向 SQLite 写账本和向 Kafka 提交偏移量是两个独立操作。

1. **先 C 后 B。** 在两者之间崩溃，重启从下一条开始。账本缺一条，组进度已经向前。
2. **先 B 后 C。** 在两者之间崩溃，重启重读当前记录。若 B 是“累计值加一”，同一笔可能贡献两次；若 B 同时在事务中检查物理收据并写业务结果，恢复可命中同一收据。
3. **输出也在 Kafka。** 事务生产者可以把目标主题输出与相应组偏移量纳入一次 Kafka 事务；下游用 `read_committed` 读取已提交结果。外部 SQLite、邮件和看板推送各有自己的提交边界。

本章采用第二种方案。一次 SQLite 事务同时保存收据和对应业务效果，然后同步提交这一条消息的下一位置。数据库写失败就停止；数据库已成功、偏移量提交失败，也停止并按持久证据恢复。再均衡时，旧成员要停止接收已撤销分区的任务，只确认已完成的前缀；延迟到达的旧任务还可能写外部服务，因此外部业务键约束仍有作用。对不可逆通知可先在同一事务中写入待发送表，再由具备幂等请求号的发送器投递。

## 29.3 行情接入、容量规划与消息契约

### 消息要携带什么

实验主题为 `market.quotes.ch29.v1` 。消息键为资产代码的 UTF-8 字节；正文为 UTF-8 JSON。固定教学来源 SYNTHETIC，`schema=1` 标记模式版本。业务物理键由资产、事件秒和修订号组成；价格用最小报价单位整数和 `scale` 表示；`seed_uid` 保留第26章账本的种子证据。`ready_s` 保留第28章教学查询服务的可用时间。真实多源逐笔接入还要纳入来源、会话和来源事件标识，以及原始发布和本机接收时间。

消费者验证模式、键值一致性、路由和时间边界。合法新版本写业务表；同版本冲突、损坏 JSON 或无效模式保留原始载荷与物理坐标。只有隔离记录也持久化后才允许越过它。这样可以把一条坏数据交给核查，同时让后续报价继续处理。若同一物理位置重新出现却具有不同载荷，应停下来核查主题实例或数据完整性。

对于宏观与舆情，分区键可以换为“发布机构、指标与报告期”或“文档来源和文档标识”。撤回新闻要和原文关联，宏观修订要保留首次发布值。若将整个主题按来源而不是按资产分区，消费者必须另行完成跨来源的资产对齐。不同的数据保留期、敏感级别与订阅权限，也是考虑拆分主题的理由。

### 算出系统能否追上开盘突发

设进入某组的速率为 $\lambda$ 条/秒，单条平均编码大小为 $s$ 字节，保留 $T$ 秒，复制因子为 $r$ ，压缩后与压缩前字节比为 $c$ 。每秒原始载荷为 $\lambda s$ ，积累 $T$ 秒后乘以压缩比和副本数，得到集群日志载荷估计：

```math
V\approx\lambda s T c r.
```

假设平均 2000 条/秒、每条 500 字节、保留 24 小时、压缩比 0.5、三副本。每秒约 1 MB 原始载荷；一天 86.4 GB；压缩复制后约 129.6 GB，均按十进制单位。索引、段未填满的余量、故障恢复和副本迁移空间另外计算。这里的数值是容量题设，实验数据只有十条。

消费者停机 $d$ 秒，积压约为 $\lambda d$ 。恢复后处理能力为 $\mu$ 条/秒，同时仍有新行情进入。每秒净消化 $\mu-\lambda$ 条，因此当 $\mu\gt \lambda$ 时，

```math
t_{\mathrm{catch}}=\frac{\lambda d}{\mu-\lambda}.
```

若到达率 2000、停机 30 秒、恢复后每秒处理 3000 条，积压 60000 条，追平还需 60 秒。把这个计算逐分区做一次：若股票所在分区每秒进入 1800 条，负责它的单个工作者只能处理 1400 条，即使另一个成员空闲，股票分区也会继续变旧。监控至少同时记录分区积压、最老待处理事件的年龄、账本拒绝原因及最后一次成功提交时间。保留策略若已清除了所需记录，应从归档补齐缺口并登记恢复边界。

### 何时值得引入 Kafka

单进程且只服务一个写者时，第26章的有界内存队列易于控制，重启恢复依靠来源重放。低频、多步事务的任务可用数据库队列表，将领取、结果与状态更新放入同一数据库。若需要多个独立订阅者从不同位置追赶、长时间保存可重放输入或跨机器分摊不同标的，分区日志的收益更明显，代价是协调器、磁盘留存、复制和消费组运维。按这些需求选型，比按每秒消息总数给出固定分界更可靠。

| 消费组 | 故障位置 | 恢复后收据 | 规范业务版本 | 最终下一位置 |
|---|---|---:|---:|---|
| audit | 正常顺序执行 | 10 | 9 | (6,4) |

打开运行目录中的 `log.db` ，下面的完整 SQL 可同时检验两种“少一条”。第一条找 unsafe 丢失的**物理位置**，第二条计算每组实际拥有的**业务版本数**。

```sql
SELECT p,o FROM log
EXCEPT SELECT p,o FROM receipt WHERE g='unsafe';

SELECT g,COUNT(*) AS versions FROM event GROUP BY g ORDER BY g;
```

**用四次调用验证三个键。** 在 `教材/code/ch29` 中用 Anaconda 运行以下完整短例。前两次调用使用同一物理位置，第三次改变位置，第四次再改变价格。运行结果依次为 ACCEPTED、REPLAY、DUPLICATE、CONFLICT。

```python

quote = dict(schema=1, source="SYNTHETIC", asset="EQ_DEMO", event_s=60,

with closing(sqlite3.connect(":memory:")) as db:

    for offset, price in [(0, 10011), (0, 10011), (1, 10011), (2, 10051)]:
        raw = json.dumps(dict(quote, price_atoms=price)).encode()
        print(apply(db, "audit", TOPIC, 0, offset, b"EQ_DEMO", raw))
```

### 本章总结

偏移量定位一次物理发布，业务键定位一次金融事件的某个版本，消费组定位一份订阅进度。三者分开记录后，系统才能解释为什么一次重启造成重读、为什么两张收据只产生一个业务版本，以及为什么进度追平的组仍可能少一笔报价。下一章将在这条日志上比较逐条、微批和批量计算。

### 分层练习与参考答案

**1．基础。** 两分区主题有两个独立组。审计组有三个成员，特征组有一个成员。稳定分配时最多有多少成员能处理此主题？消息被审计组消费后，特征组如何继续取得它？

答：审计组最多两个成员获分区，另一个空闲。特征组的一个成员可负责两个分区。两个组使用不同进度读取仍在留存期内的同一日志，合计最多三个活跃成员。

**2．位置计算。** 分区末端下一位置为 24。20 至 23 已拉取，处理按 21、23、20、22 完成，起初提交位置为 20。每次可提交到哪里？

答：依次为 20、20、22、24。前两次均缺20；20完成后连续前缀含20和21；最后22补齐，23先前已完成。拉取后直接提交24会跳过尚未持久化的结果。

**3．恢复推导。** 入流每秒 800 条，停机 45 秒，恢复后每秒处理 1200 条。10分钟留存是否足够？说明依据。

答：停机积压 36000 条，净消化率 400，90 秒追平。若故障前已追平、输入均匀且恢复持续满速，积压记录能在10分钟内取回。若故障前已落后9分半，则刚停机45秒，最老记录就可能越过留存窗口；还要核对空间上限和段清理策略。

**4．金融分析。** 股票 v1 的价格是 100.11 元，v2 是 100.51 元。v2 在分区0偏移量5。一个只允许教学秒120可用数据的回放任务，读到该位置后应如何处理？

答：保留原始物理记录，因为它是审计证据；生成截至120秒的面板时检查 `ready_s` ，v2 到86405才可用，选择 v1。若提交消费位置代表“已入审计账本”，可以正常提交；若代表“某历史决策已使用此版本”，则应把决策版本另存，不能从消费位置反推。

**5．编程。** 怎样区分同一条消息重读、同一业务重复发布、同版本改价？写出最小测试输入。

答：选一个规范 JSON，先用分区0、偏移量0处理两次，期望 ACCEPTED、REPLAY。用同一 JSON 写入偏移量1，期望 DUPLICATE。复制 JSON 更改价格、保持事件秒与版本，在偏移量2写入，期望 CONFLICT。最终应有三个物理收据、一个规范业务版本；原始价格保留。配套测试还把改价载荷放回旧位置，断言程序停止并报告物理坐标内容改变。[测试代码](./code/ch29/test_log_lab.py)

**6．工程诊断。** 生产者报告“已放入本地发送队列”，随后进程终止。根据哪项证据能向接入程序确认 Kafka 发布？发送成功后又收到来源重投怎么办？

答：让客户端处理交付回调并核对成功的代理确认，关闭时检查待投递条数和错误。若终止时结果未知，按来源事件标识重试。Kafka 协议内重试由幂等生产保护；重新读取来源后再次发送属于新的发布，落地仍按业务键核对。

**7．容量权衡。** 6 个等速分区，每分区每秒 900 条，每名消费者最多处理 1500 条/秒，组内有 4 名消费者。总处理能力看起来足够，系统会追平吗？

答：总入流5400，总能力6000。但稳定分配有成员至少负责两个完整分区，对应1800条/秒，超过1500，形成局部积压。新增成员至每个分区可独立处理，或调整每组任务成本与分区布局；验收应看每分区积压曲线和最老事件年龄。

**8．开放设计。** 把“风险等级上升时发送一封邮件”接到消费者后。如何让审计员说明每一次报警和重试？

答：以规则版本、决策窗口、资产或组合标识生成通知键，在写入决策与物理收据的同一事务中插入唯一待发送记录。独立发送器使用固定请求标识，登记尝试与回执。若邮件网关没有幂等接口，发送成功但回执丢失会留下不确定状态，需制定重试、核对与可能重复通知的策略。验收四项等权：业务决策与待发记录共同提交，两处崩溃位置可重放，回执与报警键可追溯，外部不确定状态能明确展示。
