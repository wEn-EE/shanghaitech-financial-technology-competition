# 第28章 分布式存储与数据库设计

第四篇 · 分布式系统与计算机系统架构

股票在开盘后第一分钟报 100.11 元，第二天收到更正，改为 100.51 元。此时三个人来查数据：值班员问“现在最新价是多少”，研究员问“昨日第一分钟的收益按修订数据怎么算”，评委问“模型昨日触发报警时用的是什么”。如果数据库只保留每个标的一行最新值，第一问尚可作答，后两问的证据已经被覆盖。

**学习目标。** 先修第 17 章的事件键与报价单位、第 20 章的时点有效性，以及第 27 章的副本可见性。完成本章后，应能从查询条件推导复合键和索引顺序，估算扫描页数与分区扇出，选择事务和归档的发布边界，并用同一批数据逐行核对热库与冷文件的历史查询结果。

## 28.1 关系型、时序、列式、对象和缓存存储

### 先在纸上写出查询

写下查询的输入、输出和顺序，才能判断某种布局是否合适。

| 查询 | 输入 | 返回及验收条件 |
|---|---|---|
| 某资产最新报价 | 资产、事件时间上界、系统可用时间上界 | 在两个上界内选事件时间最大的一笔，同一事件取最高可见修订；无记录就返回缺失 |
| 多资产窗口 | 事件时间半开区间及决策截止时点 | 每个资产、每个逻辑事件至多一条可见版本，结果次序确定 |
| 历史决策审计 | 决策标识或特征名、参数版本、截止时点 | 可从结果定位输入版本、价格尺度、种子或原始事件，重算得到同一特征 |

**关系型数据库（relational database）**用表、键和约束表达对象间的关系。一项资产可以有许多报价，每条报价指向一种资产；这样，资产单位可以由资产主数据统一管理。数据库通过索引和连接找到相关行。订单、版本清单、告警确认和权限变更常需要把几项更新放进同一事务。只更新了一半的数据，即使查询很快，也不能用于对账。

**时序数据（time-series data）**以时间为查询轴。时序存储通常按时间块组织数据，在块内按序列标识和时间排列，并可为长期数据维护降采样结果。股票代码、来源、频率等标签组合定义一条序列。假设有 400 个标的、3 个来源、2 种频率，所有组合都存在时已有 2400 条序列。再把逐消息的唯一请求号设为序列标签，序列数将接近消息数。请求号适合存作审计字段。对滚动最高价要保留各块最高价；只有均值的历史块无法还原峰值。

**行式与列式（row-oriented / column-oriented）**描述同一批数据的物理布局。行式把一条记录的字段放得较近，取一笔完整事件很自然。列式把同列值集中保存，适合按时间段读取少数列并聚合。Parquet 把文件分成行组（row group），每个行组里每列有一个列块（column chunk），列块内再分页。只取价格和时间时，读取器可选择相应列块。同一类字段集中也给字典编码和压缩创造条件。[Apache Parquet 格式概念](https://parquet.apache.org/docs/concepts/)

**对象存储（object storage）**按对象键访问字节内容。可以把 Parquet 文件作为一个对象，也可以保存公告原文、原始行情包和模型文件。查询某个历史区间时，读者先查清单获得文件键和覆盖范围，再读对应文件。对象键、文件格式和数据库承担三个不同职责，选用 Parquet 并不会自动获得跨文件事务。

**缓存（cache）**保存可以从权威数据重新生成的结果。例如键中包含资产、币种、查询口径和模型版本，值中保存价格、事件时间及已应用的版本。缓存命中后仍要检查请求规定的最低版本和最大年龄。实时时价缓存若只按资产编号建键，历史请求也使用这个键，就可能把今天的更正带回昨天。对时点回放，可按不可变快照标识缓存，或直接读取相应版本。[第27章的读契约](./27_第27章_分布式系统、CAP与一致性.md)

## 28.2 分区、索引、事务、复制与冷热分层

### 从磁盘页推导访问代价

设有 $N$ 条定长记录，每条宽 $w$ 字节，一页可用载荷 $B$ 字节，且一条记录完整放在一页内。暂忽略页头和碎片。每页可放 $b=\lfloor B/w\rfloor$ 条；要容纳全部记录，再向上取整，需页数

```math
P=\left\lceil\frac{N}{b}\right\rceil.
```

若 $B=4096$ 、 $w=128$ 、 $N=1048576$ ，每页 32 条，共 32768 页。无有用索引且顺序扫描所有记录时，需要访问这些数据页。若只求两个合计 16 字节的字段，在紧密排列、忽略压缩和元数据的理想列式布局中，扫描载荷由 128 MiB 降到 16 MiB。这是字节预算，实际耗时还包含缓存命中、解压、请求次数、谓词判断和结果传输。

**B+ 树索引（B+ tree index）**由内部页引导至有序叶页。若每叶平均容纳 $L$ 个索引项，先需约 $\lceil N/L\rceil$ 个叶页。假设每个内部节点稳定保持扇出 $F$ ，向上每层约把页数除以 $F$ 。需要的内部层数约为

```math
h=\left\lceil\log_F\left(\left\lceil N/L\right\rceil\right)\right\rceil.
```

取 $L=128$ 、 $F=128$ ，得 8192 个叶页、64 个上层页和 1 个根页。一次定位经过根、内部页和叶页，随后顺序扫过命中范围。若叶项只含行指针，还要取数据页；当索引自身包含查询所需各列，它就成为该查询的**覆盖索引（covering index）**。这个计算用来理解扇出，具体数据库的页格式和组织由引擎决定。[Berkeley CS 186，B+ Trees](https://cs186berkeley.net/notes/note4/) · [SQLite 查询规划，§1.6—1.7](https://www.sqlite.org/queryplanner.html)

复合索引按字典序排列。将 `(asset,event_s,revision)` 写在纸上，同一资产的相邻时间会聚在一起，适合单资产查询。要查“所有资产在某一分钟内的物理版本”，时间放第一列更容易定位连续范围。索引 `(event_s,asset,price_atoms)` 还能直接提供这三列，并按时间、资产顺序输出。每增加一个索引，插入或改动被索引数据都要维护另一套结构。索引的收益应和写入成本、磁盘预算一起量。

### 分区键决定请求会去哪里

**分区（partitioning）**把一张逻辑表按规则拆成若干部分；分片（sharding）将数据分摊到不同节点。同一台机器也可以分区。**复制（replication）**为同一份数据维护副本。如果把全部数据分成四片，每片放三份，则共有十二个分片副本，单个副本约持有四分之一的数据，整个集群的记录载荷约为原始数据的三倍。此估算假设四片均衡，暂不计索引、日志和备份。

按教学日分区，宽度为 $D$ 秒。事件秒数为非负整数，区间取左闭右开 $[a,b)$ ，且 $a\lt b$ 。首分区编号为 $\lfloor a/D\rfloor$ ，末分区编号为 $\lfloor(b-1)/D\rfloor$ ，两者之差加一就是访问分区数。最后一秒属于旧分区，边界正好为新日的首秒属于新分区。这一推导使用整数秒；生产系统可直接用区间相交条件 `partition_start < b AND partition_stop > a` 。实际交易日按交易日历映射，夜盘的交易日可能与自然日期不同。[PostgreSQL 18，§5.12](https://www.postgresql.org/docs/18/ddl-partitioning.html)

按资产哈希分片能把指定资产路由到单片，却会使全市场扫描同时访问许多节点；一个极活跃标的仍可能独占一片的大部分写入。按日期分区利于历史范围、迁移和过期清理，所有新写又会集中到当前日期。可以在日期内按资产分桶。决定桶数前，统计每桶每秒字节数、最大标的占比和典型查询触达桶数。少量数据直接建索引，常比维护大量小分区更省事。

### 在什么边界发布数据

**事务（transaction）**把一组操作作为提交或回滚的单位。金融监控常把事件写入和消费位置推进放进同一事务。先推进位置再写事件，中途崩溃会跳过消息；只写事件然后崩溃，则需要按业务键核对重放。**隔离（isolation）**决定并发读者能看到哪些中间状态。本章在同一个 SQLite 读事务中导出所有分区，读到的数据库状态保持一致。数据库快照解决“导出过程中看到了哪次提交”；数据自身的 `ready_s` 解决“历史模型当时能读到什么”。两个条件都需要。[SQLite 的隔离与快照](https://www.sqlite.org/isolation.html)

**热层（hot tier）**服务频繁点查和近期更新，**冷层（cold tier）**服务长期留存和批量查询。迁移可以分成四步：

1. 选定数据库快照及导出范围，把每一版数据写入本次运行独占的文件目录。
2. 为每份文件登记时间边界、行数和内容摘要。
3. 文件写完后再发布清单。读者从已发布清单寻找数据，避免把导出一半的目录当作完整批次。
4. 在两个截止时点逐行比较冷热结果。保留策略另行决定何时回收热数据。

实验在同一文件系统内替换清单文件。跨机器对象存储部署可写入不可变对象键，再用带条件的目录更新发布一个清单版本；发布前崩溃留下的孤立对象按归属清理。若旧日行情很久以后才修订，可为旧分区追加更正文件并发布新清单，同时保留旧清单供审计。副本会传播误写或误删，恢复到事故前状态还需要独立备份及恢复演练。

## 28.3 金融事件、特征及审计查询的存储组合

### 价格的三个顺序

本章用一资产一教学分钟一笔报价的人工数据。逻辑事件键为 `(asset,event_s)` ，物理版本键增加 `revision` 。`price_atoms` 为最小报价单位整数，按 `scale` 还原价格。`ready_s` 表示该版本可供本实验查询服务使用的教学秒数。`seed_uid` 回指第 26 章的原始种子报价。真实逐笔行情可能在同一微秒有多笔成交，应保留来源、会话、序号或供应商事件键。时间戳单独充当主键会把不同交易误判为冲突。

下面是实验中最容易写反的三条记录。每行的含义都是“关于某一事件，在这个时点起可读的一个版本”。

| 资产 | 事件秒 | 版本 | 可用秒 | 价格 |
|---|---:|---:|---:|---:|
| EQ_DEMO | 60 | 1 | 61 | 100.11 |
| EQ_DEMO | 86400 | 1 | 86401 | 100.10 |
| EQ_DEMO | 60 | 2 | 86405 | 100.51 |

在 86405 秒做最新价查询，最后到达的是旧事件的修订，时间最近的事件仍为 86400 秒。于是最新价为 100.10。查询“事件 60 的最新修订”才得到 100.51。查询“决策时点 120 所见的事件 60”则得到 100.11。

**选择的顺序很重要。** 先保留事件落在目标窗口且在截止时点已经可用的版本，再在每个逻辑事件内选最高修订号。若先在全库选最高修订，再剔除尚未可用的版本，事件 60 在历史回放中会整笔消失。若先选最高修订且省略可用时间过滤，便把次日信息提前写入昨日特征。实际系统若允许撤回，还须把撤回也作为版本参加选择，选中后再解释其状态。

```sql
SELECT asset, event_s, revision, price_atoms, scale, seed_uid, ready_s
FROM (
    SELECT q.*,
           ROW_NUMBER() OVER (
               PARTITION BY asset, event_s ORDER BY revision DESC
           ) AS pos
    FROM quotes AS q
    WHERE event_s >= :lo AND event_s < :hi AND ready_s <= :cutoff
)
WHERE pos = 1
ORDER BY asset, event_s;
```

这里 SQL 中的 `PARTITION BY` 为窗口函数分组，表的磁盘分区由存储层另行决定。把两者混为一谈，往往会误以为写了窗口函数就已经减少了文件读取。

### 特征和报警怎样找回证据

以开盘首分钟简单收益为例，模型需要第 0 秒和第 60 秒两条报价。初价为 100.10，首报为 100.11，以分为单位计算得到收益 $1/10010$ ，约为 0.00999%。次日更正后，差值变为 41 分，收益为 $41/10010$ ，约为 0.40959%。两份结果针对同一市场区间，信息截止时点不同。程序把特征名、截止秒数、两个物理版本键、结果或缺失状态一并返回。阈值若为 0.2%，昨日首报未越线，修订序列越线；审计表应保留昨日判断，给修订计算分配另一结果版本。

平台扩展时，原始新闻和报价包可存入不可变对象，关系表登记来源、授权范围、获取时间及内容摘要。训练面板用列式快照并携带特征定义版本。在线结果按资产和时间索引，预警引用具体特征批次、模型及规则版本。一次审计从报警编号沿这些外键走回输入，避免在庞大的行情表上猜测“那时应该用了哪条数据”。多资产聚合还要核对计价币种和价格尺度，黄金、汇率和股票的 `price_atoms` 不能直接相加。

## 28.4 实验：同一笔跨日修订的冷热对账

实验只读使用第 26 章 SQLite 账本里的四资产种子报价。已有 Anaconda 的 SQLite 3.45.3 与 PyArrow 25.0.1 分别承担行式查询和 Parquet 文件读写。为每种资产生成三个教学日，每日仅生成开头 60 个分钟点；每分钟在种子价的整数单位上加分钟序号。加上一条股票跨日修订，得到 $4\times3\times60+1=721$ 个物理版本，涉及 720 个逻辑事件。教学日长 86400 秒，生成路径、时钟和修订均为人工设定。[完整程序](./code/ch28/storage_lab.py) · [测试](./code/ch28/test_storage_lab.py)

在仓库根目录运行。若已有上一章用过的第 26 章账本，可以从第二条命令开始。

```powershell
D:\Anaconda\python.exe -X utf8 教材/code/ch26/stream_lab.py
$seedDb = Get-ChildItem 教材/code/ch26/runs -Recurse -Filter market.db | Sort-Object LastWriteTime -Descending | Select-Object -First 1
D:\Anaconda\python.exe -X utf8 教材/code/ch28/storage_lab.py $seedDb.FullName
D:\Anaconda\python.exe -X utf8 -m unittest discover -s 教材/code/ch28 -v
```

**第一步，验收索引。** 程序对第二天最初两分钟查三列，按事件秒和资产排序。建索引前后使用相同参数并比较所有返回行。这是考察物理版本扫描的查询；用于模型的逻辑版本查询另有上述截止条件。

```sql
SELECT event_s, asset, price_atoms FROM quotes
WHERE event_s >= 86400 AND event_s < 86520
ORDER BY event_s, asset;
```

本机返回 8 行。建索引前执行计划为 `SCAN quotes` 和 `USE TEMP B-TREE FOR ORDER BY` ；建索引后为 `SEARCH quotes USING COVERING INDEX by_time (event_s>? AND event_s<?)` 。前者扫表并为排序建立临时结构，后者从时间索引定位范围，所取字段都在索引里。要量化加速倍数，还需固定数据量、冷热缓存状态和并发度，重复测量尾延迟与写入开销。本实验验收的是执行路径及结果相等。

**第二步，验收文件裁剪。** 导出器按事件日生成三个 Parquet 文件，行组最多 64 行，另存 `manifest.json` 。读者先用时间范围排除不相交文件，再为选中文件核对 SHA-256 摘要，读取七列以重建并核对版本。查询第 0 天的 `[0,120)` 只选中 `day-0.parquet` 。为验证文件完整性，教学实现特意读取整个选中文件计算摘要。随后解码本次核对所需的全部七列。输出中的文件数反映分区裁剪，实际物理读取字节数还包括完整性检查。

**第三步，验收修订与特征。** 热查询用 SQL 窗口函数，冷查询用 Python 按逻辑键保留最高可见修订。两条路径在以下两个截止时点逐行比较资产、事件秒、版本、最小单位整数、价格精度、种子来源和可用秒。它们使用不同实现，可检出边界和版本处理的偏差。

| 查询 | 热库与冷文件实际结果 |
|---|---|
| 区间 [0,120)，截止 120 | 8 个逻辑事件，股票第 60 秒为 v1，10011 分 |
| 同一区间，截止 86405 | 仍为 8 个逻辑事件，同一笔股票改为 v2，10051 分 |
| 最新价，事件与可用上界均为 86405（热库） | 事件 86400，v1，10010 分 |

**读者短实验。** 在 `教材/code/ch28` 目录，用已有 Anaconda 运行以下代码。它在内存中建表，观察修订可用前一秒和恰好可用时的变化。程序用一个人工种子，输入和主实验的股票种子价格相同。

```python
import sqlite3
from contextlib import closing
from storage_lab import DAY, equity_feature, load

with closing(sqlite3.connect(":memory:")) as db:
    load(db, [("EQ_DEMO", 10010, 2, "exercise")])
    for cutoff in (60, 120, DAY + 4, DAY + 5):
        answer = equity_feature(db, cutoff)
        print(cutoff, answer["status"], answer.get("inputs"), answer.get("value"))
```

60 秒时第二条报价还差一秒才可用，输出缺失。120 和 86404 秒返回相同版本对。86405 秒只改变第二个输入版本，收益随之改变。每次主实验创建新的运行目录，内有热库、三个冷文件和清单；原始账本不会接收实验写入。此处用本地文件系统模拟对象布局，跨节点网络延迟和对象服务故障属于部署实验的测量项。


### 对账练习：整数相同，价格或证据仍可能不同

在仓库根目录执行 `D:\Anaconda\python.exe -X utf8 -m unittest discover -s 教材/code/ch28 -p test_storage_lab.py -v`。其中 `test_cold_scale_source_and_time` 每次只改一个字段，把改过的数据导出到新的临时目录，再把热库还原。此时清单摘要与文件相符，文件可以正常解码；错误发生在数据含义上。冷热分别按自己的逻辑选择可见版本，再按同一字段顺序比较。

| 实验 | 热库 | 冷文件 | 验收证据 |
|---|---|---|---|
| 只改精度 | 10011，scale=2 | 10011，scale=3 | 指出 scale；还原价格分别为 100.11、10.011 |
| 只改来源 | seed | another-seed | 价格相同，差异中指出 seed_uid 以及两边的来源 |
| 只改可用秒 | 61 | 62 | 截止 120 时两边都能选到该行，仍应指出 ready_s |

要观察诊断消息，在 `教材/code/ch28` 目录运行下列短程序。每轮都重新建立同一份热数据；先故意改错一条首报再导出，把热库恢复为正确值后才发起对账。若直接破坏文件字节，程序会先报告摘要错误，实验就走不到逐字段对账这一步。

```python
import sqlite3
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory
from storage_lab import archive, compare, load

for field, wrong, original in (("scale", 3, 2), ("seed_uid", "another-seed", "seed")):
    with TemporaryDirectory() as tmp, closing(sqlite3.connect(":memory:")) as db:
        load(db, [("EQ_DEMO", 10010, 2, "seed")])
        sql = f"UPDATE quotes SET {field}=? WHERE event_s=60 AND revision=1"
        with db:
            db.execute(sql, (wrong,))
        archive(db, Path(tmp))
        with db:
            db.execute(sql, (original,))
        try:
            compare(db, Path(tmp), 60, 61, 120)
        except AssertionError as difference:
            print(difference)
        else:
            raise AssertionError(f"未检出 {field} 偏差")
```

价格等于最小单位整数除以 10 的 scale 次方。计算相邻两期收益时，程序先按各期自己的精度还原价格。例如 10011 配两位小数与 100110 配三位小数都代表 100.11；两次输入以同一价格计入收益。来源标识的作用可以在真实章内实验库上亲自验证。下面的短程序取最近一次第 28 章实验，查出股票第 60 秒首报的种子标识，再用它到第 26 章账本取原始收据。先运行本节主程序，生成带有导入记录的新热库。表 import_source 记录本次读入的账本路径。即使后来重跑了第 26 章，也能按原路径查回当时的账本。

```python
import sqlite3
from pathlib import Path
from contextlib import closing

paths = Path("教材/code/ch28/runs").glob("*/hot.db")
hot_path = max(paths, key=lambda p: p.parent.name)

with closing(sqlite3.connect(hot_path.resolve().as_uri()+"?mode=ro", uri=True)) as hot:
    source_path = Path(hot.execute("SELECT path FROM import_source").fetchone()[0])
    uid, atoms, scale = hot.execute(
        "SELECT seed_uid,price_atoms,scale FROM quotes "
        "WHERE asset='EQ_DEMO' AND event_s=60 AND revision=1").fetchone()
with closing(sqlite3.connect(source_path.resolve().as_uri()+"?mode=ro", uri=True)) as source:
    receipt, raw = source.execute(
        "SELECT receipt_id,raw FROM event JOIN receipt ON receipt_id=first_receipt_id "
        "WHERE event_uid=?", (uid,)).fetchone()
print(uid, atoms, scale, receipt, raw.decode())
```

从原始收据可以读到种子报价 100.10。热表的 100.11 是以该种子加一个最小报价单位生成的首分钟人工值。于是既能复核数值换算，也能说明这条输入如何产生。

### 本章总结

数据库设计首先要把对象认清：一张收据、一个逻辑事件、该事件的一次修订、某次决策选中的输入，各自有不同的键。然后才能决定哪些键用于事务，哪些键用于排序，哪些键用来裁剪冷文件。检验设计时，先核对价格、版本和截止时间，再用查询计划检查数据库为得到这些结果做了多少工作。

### 分层练习与参考答案

**1．基础。** 同一资产同一微秒出现两笔不同成交，程序把第二笔当成修订 2。怎样判定错误？

答：查来源会话和成交编号。两个独立编号对应两个逻辑事件，都应参与成交量；修订号用于描述同一事件被更正。先统一来源身份，再建立物理版本唯一约束，测试中同时放入同微秒两笔成交及其中一笔的修订，最终应保留两个有效事件。

**2．页数推导。** 8192 字节页存放 200 字节定长行，共 100001 行，每页留 192 字节作管理信息。全扫需要多少数据页？

答：可用 8000 字节，每页装 40 行。2500 页恰好装 100000 行，余下一行单占最后一页，共 2501 页。若只读小部分字段，行式全扫仍要访问含这些记录的页。缓存命中会减少磁盘读取次数，估算时应写清计量单位。

**3．分区边界。** 取 $D=86400$ ，整数秒区间 [86399,86401) 与 [86400,86401) 各触达哪些分区？

答：前者含 86399 和 86400 两秒，对应分区 0 和 1；后者只含 86400，对应分区 1。若两个相邻文件都包含上边界，一条恰在午夜的消息会在跨文件聚合时重复。测试还应覆盖空结果和落在边界上的修订。

**4．SQL 反例。** 先按事件选最高修订，再用 `ready_s<=120` 过滤，对事件 60 会得到什么？写出修正步骤。

答：全库最高版本是 2，`ready_s=86405` ，过滤后该事件消失，首分钟收益因此缺失。应先按事件区间和截止时点取候选，在每个逻辑键内部按修订号降序编号，选第一行。本章 SQL 即完整解法。分别在 60、61、86404、86405 秒断言缺失、v1、v1、v2。

**5．金融分析。** 把改价幅度除以修订前首分钟末价来计算“修订后首分钟收益”，问题在哪里？

答：这一算式衡量两次报送价格的相对差异，其分母为 100.11。首分钟收益的基期是第 0 秒的 100.10。应分别用 100.11 和 100.51 除以 100.10 再减一。两次收益相差 $40/10010$ ，约 0.39960 个百分点。报警记录需保存分母所用版本，才能在基期价格也被修订时重新解释差异。

**6．编程与可靠性。** 怎样验证导出文件损坏后程序不会交付看似正常的面板？

答：在临时目录生成快照，对本次查询必选的文件末尾追加一个字节，然后查询 [0,1)。读者根据清单摘要重新计算，检测不一致后抛出错误。测试应断言该错误发生在返回结果前，并只改动自己生成的文件。完整实现见 `test_corruption` 。同一试验目录内的清单被视为可信；外部存储还需保护清单的写权限与版本。

**7．容量与路由。** 一天原始载荷为 80 GiB，保留 10 天热数据，均匀分四片，每片三副本。如果索引再占数据载荷的 25%，需预留多少空间？

答：十天载荷 800 GiB，每片 200 GiB，每份副本连索引为 250 GiB，十二份合计 3000 GiB。日志、备份、压缩比、峰值倾斜及维护时重建索引的临时空间另外核算。若一个节点放了三份不同分片的副本，该节点的基础预算为 750 GiB。

**8．开放设计。** 一年历史数据已归档，近日收到六个月前的官方更正。怎样让今天的研究得到新值，同时能够逐笔复核半年前的报警？

答：为原逻辑键追加版本，保留官方发布时间和本系统实际可用时间。为涉及的日期生成带修订的分区或增量文件，生成新清单；原清单继续供原报警读取。研究任务显式指定新截止点和清单版本，重算受影响的滚动窗口，记录输出及依赖。评分各占四分之一：原始材料及旧结果可追溯，更正仅对合适截止时点可见，新清单发布前读者看不到半批文件，重放测试能给出两组确定的输入键与数值。
